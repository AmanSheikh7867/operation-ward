# Assumptions, Constraints, and Technical Limitations

## 1. Clinical Limitations & Regulatory Disclaimer

- **Prototype Status**: Operation Ward Zero is a proof-of-concept hackathon prototype designed for technological and UI demonstration. It is **NOT** a clinically validated medical device and has not received FDA 510(k), CE mark, or SaMD certification.
- **Synthetic Training Data**: The machine learning model was trained entirely on synthetic vital-sign distributions with rule-generated target labels. It demonstrates algorithmic pipeline design, explainability via SHAP, and real-time inference latency. It has never been evaluated on clinical trial datasets (e.g., MIMIC-IV, PhysioNet).
- **Snapshot Prediction vs. Deterioration**: The model calculates an instantaneous risk score based on the current 5-vital snapshot. It does **NOT** forecast 24- to 48-hour future clinical decompensation or septic shock trajectories. True prospective deterioration prediction requires longitudinal time-series models (e.g., Temporal Fusion Transformers, LSTM-RNNs) trained on patient health record histories.

---

## 2. IoT & Telemetry Constraints

- **Software Simulation**: Biometric readings are generated by the software simulator (`iot/sensor_simulator.py`) using calibrated Gaussian distributions with bounded noise. No physical hardware sensors (e.g., MAX30102 pulse oximeter, DS18B20 thermometer) are connected in standard demo mode.
- **MQTT Public Broker**: For zero-setup hackathon demonstrations, the system defaults to HiveMQ's public broker (`broker.hivemq.com:1883`). Public brokers must **never** be used for real patient identifiable data (PHI). Production deployments require private Mosquitto brokers with TLS 1.3 encryption and mutual certificate authentication.
- **Stale Data Watchdog**: The system assumes sensor data is stale if no packet arrives within 25 seconds. In real hospital environments, sampling rates may range from 1 Hz (ICU monitors) to once every 4 hours (general ward rounds).

---

## 3. AI Caregiver Assistant (Groq LLM) Constraints

- **Non-Diagnostic Guardrails**: The Groq assistant operates under strict system prompt constraints: it must never offer medical diagnoses, recommend prescription drug dosages, or alter physician care plans.
- **Hallucination Mitigation**: The LLM prompt explicitly binds the assistant to the verified live vital signs and system-generated alert reasons. If the Groq API times out or is unreachable, the system falls back to pre-programmed clinical triage instructions.
- **Multilingual Support**: Natural language translations across English, Hindi, and Hinglish are generated in real-time. Caregivers should confirm critical medical instructions in their preferred clinical language.

---

## 4. Database & Persistence Assumptions

- **Cloud Latency**: Supabase requests timeout at 5 seconds (`DB_TIMEOUT_S=5`). When connectivity is interrupted, the in-memory ring buffer holds up to 5,000 records. If the buffer exceeds 5,000 items before database recovery, the oldest records are dropped to protect system memory.
- **Security Assumption**: Supabase service-role keys are strictly kept on the FastAPI backend and never forwarded to the browser or logged to stdout.
